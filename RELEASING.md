# Releasing nestro-ui-kit (Changesets)

Этот документ описывает, как правильно вносить изменения в UI-kit и выпускать версии.

## TL;DR (самое короткое)
1) Перед PR: `npm run changeset` → выбрать bump (patch/minor/major) → описать изменения → закоммитить changeset вместе с кодом
2) Релиз: `npm run version-packages` → коммит `chore: release` → собрать артефакт `npm run pack` → перенести `.tgz` в контур

---

## 1. Правила версий (SemVer)
UI-kit версионируется по SemVer: `MAJOR.MINOR.PATCH`.

### PATCH (x.y.Z)
Исправления без breaking changes:
- баг/фиксы
- правки стилей без изменения публичного поведения
- улучшение типизации без изменения API

Пример: `1.0.11 -> 1.0.12`

### MINOR (x.Y.0)
Новые возможности без поломок:
- новый компонент
- новый проп/слот/ивент, совместимый назад
- новые токены/варианты тем

Пример: `1.0.11 -> 1.1.0`

### MAJOR (X.0.0)
Любой breaking change:
- переименование/удаление props/events/slots/components
- изменение поведения по умолчанию, из-за которого ломается UI у потребителя
- изменение публичных CSS-классов/токенов, на которые завязаны проекты
- изменение структуры exports/entrypoints

Пример: `1.9.0 -> 2.0.0`

---

## 2. Что считается публичным API
Публичным контрактом UI-kit считаем:
- exports компонентов (`src/index.ts` и публичные entrypoints)
- props / events / slots компонентов
- публичные CSS-переменные/токены, заявленные в документации
- типы (d.ts), если они используются напрямую
- файл стилей, подключаемый (`nestro-ui-kit.css`)

Если это меняется несовместимо — это MAJOR.
